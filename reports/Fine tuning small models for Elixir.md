# Measure Elixir first, then tune Ornith

A fine-tuned 9B will not out-solve a contemporary 35B+ model on agentic Elixir on any evidence available today: nothing published shows a 5–15B model doing that in any language, and tuning has closed only 16–42 % of the 9B gap to open giants on hard benchmarks. The speed case is gone as well, because Qwen3.5-9B is estimated at 19–23 tok/s at Q4_0 on the rig against Flint's measured 44.6–45.9, and a 3–5× edge exists only against dense 27B models. What is winnable is a tuned model that beats its own base, older general models and, unproven, Flint on held-out Elixir tasks, and that model is more likely a tuned Ornith-1.5-35B than a 9B. Elixir tuning has been tried about ten times and measured twice, never inside an agent loop, so a real agentic result would be a first for any language. The owner's dataset is well verified but holds 335 independent tasks, and it is not cleared for training under the owner's own rule because Claude wrote it, so its best use is evaluation. Agentic data has to be built from scratch with open-weight teachers run locally. The first step is an evaluation lane, then a docs context file, and only then training. All wall times below are estimates at roughly ±40 %, none measured on this machine.

## Six direct answers to the owner's questions

**Is it possible?** Partly, and the split matters. Tuned small models already beat big general ones at narrow, output-shaped work: 224 of 310 fine-tunes beat GPT-4, with the clearest wins on classification ([LoRA Land](https://arxiv.org/pdf/2405.00732)), and small language tunes beat far larger models on niche languages such as Pharo and COBOL. On hard agentic work the answer is no: **no published 5–15B tune beats a contemporary 35B+ model on agentic coding success**, and Ornith's own same-recipe curve still runs 47.5 / 59.6 / 65.1 on SWE Pro from 9B to 35B to 397B ([Ornith](https://github.com/deepreinforce-ai/Ornith-1)). It would take four things, in this order: an Elixir test the model never trained on, thousands of clean agent sessions, a base strong enough to be worth teaching, and the discipline to stop when the measured gain does not appear.

**Has anyone tried it?** Yes. Elixir has about ten attempts and **two measured results**. The best is jmarceno's October 2026 pair, which took Gemma 4 12B and Qwen2.5-Coder-3B from 31/128 to 46/128 and 45/128 on a private single-module harness ([Gemma card](https://huggingface.co/jmarceno/Elixir-Gemma-4-12B), [Qwen card](https://huggingface.co/jmarceno/Elixir-Qwen2.5-Coder-3B)). The other is a 2025 workshop paper with weak, mixed gains on very small models ([ACL SRW](https://aclanthology.org/2025.acl-srw.57.pdf)). Other languages show gains where the base is weak: +9.9 to +16.2 points on Kotlin ([JetBrains](https://arxiv.org/html/2405.19250v1)), +44 to +47 on COBOL ([COBOL-Coder](https://arxiv.org/html/2604.03986v1)) and up to +54 on Gleam ([Giagnorio et al.](https://arxiv.org/html/2606.16827v1)). **Nobody has measured a language-specific tune in a multi-turn agent loop, for any language.**

**Which models can be fine-tuned?** Qwen3.5-9B is the easiest: Apache-2.0, with Unsloth and Axolotl recipes and a BF16 LoRA listed at 22 GB, with no sequence length stated ([Unsloth](https://unsloth.ai/docs/models/qwen3.5/fine-tune.md)). Ornith-1.5-9B and MiMo-V2.6-Distill-Qwen-9B report much stronger agentic starts and belong in the baseline. Ornith-1.5-35B-A3B (MIT) can be tuned across four 3090s and is the likely end product. **Flint cannot be tuned today**, because its card says the Transformers modeling code is not included yet ([Flint](https://huggingface.co/RecursiveSI/flint)).

**How long on 5 × RTX 3090?** A LoRA of 20k short samples for three epochs takes about 22 hours and €10. One epoch of 2,000 agent sessions takes about 23 hours. A 1/8-scale multi-turn RL run takes about 9 days, and DeepSWE-scale RL about 2.5 months, which rules it out. **Every one of these is an estimate at roughly ±40 %, and none was measured on this machine.**

**Is the data good, or should it be agentic?** Both statements hold. The data is unusually well verified, but its 14,803 exportable rows reduce to 335 root tasks from 83 ideas, 54 % of them GenServers, and no row teaches a tool loop. **Prepare agentic data, keep the owner's set for evaluation, and do not spend the next GPU block on more prompt→answer SFT.**

**Where to start?** With evaluation, not training: three seeds of the candidate models on the owner's Elixir SWE Bench, Flint's two missing seeds, then a docs context file on the best base. That costs days, needs no decision on the dataset, and can end the project cheaply. The first training run is a 9B recipe pilot on clean agent sessions.

## Clean agent sessions on Ornith beat every other option

The options differ mainly in what they teach, and the evidence sorts them clearly. Context is nearly free and targets the knowledge gap directly. Trajectories teach the loop. RL is the costliest and the least proven on this hardware. Costs are estimates, and the expected effects are analogies from other languages or from Python.

| Option | Cost (est.) | Expected effect | Main risk | Verdict |
|---|---|---|---|---|
| **A. Context only:** docs index and usage rules on Ornith-35B or Flint, no training | Days of bench work | Largest lift per euro on API gaps: 53 → 100 % at Vercel; +15 to +23 points on Ash | Fixes facts, not skill; no Elixir study of it exists | **First.** Every later arm must beat this one |
| **B. SFT on the owner's core set** (2,600–3,200 rows), 9B | ~8 h for 3 epochs | About +11 points on single-turn tasks, by analogy with jmarceno; agentic effect unmeasured | Not cleared; no evidence inside a tool loop | Only after a provenance verdict, never the main stage |
| **C. Curated Hex code as a knowledge stage,** from the base checkpoint | ~11 h per 30M-token epoch | Kotlin +11.8 on 25K curated files; raw corpora give +1 to +3 | Instruction loss; transfer step unreplicated | Pilot arm; the clean substitute for B |
| **D. Clean trajectories, 9B** (2,000 kept sessions) | 30–45 h sampling, 12–23 h per epoch | +5 to +13 points on hard benchmarks, by analogy | Weak start; SFT alone hurt this base on TB Lite | **Second.** It proves the recipe cheaply |
| **E. Clean trajectories, Ornith-1.5-35B** | Four cards, roughly 1.7× the 9B's time | Same data, far stronger start, faster on the rig (est.) | LoRA on fused experts is immature | **Third, and the likely product** |
| **F. Single-turn RL with `mix test`** | 28 h for 300 iterations, 3.9 d for 1,000 | +4 to +14 points at 0.6–1B on a 3090; no 9B result | Short-task overfit; harness provenance | After D, on clean tasks |
| **G. Multi-turn RL** | 2–5 d per 60-step arm | Unknown at this batch size | No precedent on consumer GPUs | Last, and gated |

The sources for these rows are Vercel's evals ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)), Ash's flagship report ([Ash](https://raw.githubusercontent.com/ash-project/evals/main/reports/flagship.md)), Tencent's retrieval comparison, where BM25 beat tuning 53.76 to 44.20 on completion ([Tencent](https://arxiv.org/html/2505.15179v1)), the 3090 RL paper ([Skopin and Kotelnikov](https://arxiv.org/html/2605.30478v1)) and the Tmax paper ([Tmax](https://arxiv.org/html/2606.23321)).

**The recommendation is A, then C and D together as a pilot, then E.** Two caveats keep this honest. Option D's +5 to +13 comes from runs far larger than this plan: MiMo's 9B used 77.4B tokens ([MiMo](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Distill-Qwen-9B)), about 2,000 times the 40M tokens of 2,000 sessions. And the headline +8 to +21 point gains for trajectory training came from old bases that could not run a tool loop at all, so they will not repeat on a modern base. The gain that remains is Elixir knowledge plus language-specific tool habits, which is exactly what context competes with. On a modern base, plain imitation can also go backwards: SFT took Qwen 3.5 9B from 41.9 to 35.5 on TB Lite ([Tmax](https://arxiv.org/html/2606.23321)).

## "Better than bigger" hides three claims, and one is not winnable

**(a) Beating a contemporary 35B+ on agentic Elixir: no precedent at 5–15B.** The size gap survives equal treatment. On equal data, 7B against 32B was 15.2 against 40.2 on SWE-smith ([SWE-smith](https://arxiv.org/html/2504.21798v2)) and 19.0 against 34.4 on R2E-Gym ([R2E-Gym](https://arxiv.org/html/2504.07164v1)). Ornith's same-recipe 9B and 35B sit 12 points apart on SWE Pro and 21.6 on Terminal-Bench 2.1 ([Ornith](https://github.com/deepreinforce-ai/Ornith-1)). Retries do not close it: 16 rollouts with a verifier lifted an 8B only from 42.2 to 49.6 ([SWE-Lego](https://arxiv.org/html/2601.01426v2)), where independent attempts would reach 99.98 %, so hard tasks are out of reach rather than unlucky. The decisive point is logical: **tuning is not a small-model privilege.** Whatever Elixir data gives a 9B, it can also give a 35B, so the fair opponent of a tuned 9B is a tuned 35B.

One opening remains, and it is specific to Elixir. Flint scores 74.2 on SWE-bench Verified and 30 % on the owner's bench, and Ornith-1.5-122B scores 30–35 %, which hints that Elixir knowledge rather than general skill limits both. Flint also cannot be tuned. So a tuned Ornith-1.5-35B, or even a tuned 9B, could plausibly pass Flint on this bench. That result would be unprecedented, and it is a hypothesis to test rather than a forecast. Qwen3.8-Flash-Next at 50–55 % and Claude at 88–90 % are not realistic targets.

**(b) Beating older or general models: already done.** Tmax-9B beat GPT-OSS 120B 27.2 to 18.7 on Terminal-Bench 2.0, while staying far below GLM 5 at 52.4 ([Tmax](https://arxiv.org/html/2606.23321)). Pharo's tuned 7B beat Qwen3 Coder 480B and Claude 4.5 Sonnet on one metric ([Pharo](https://arxiv.org/pdf/2607.04939)). Rust's tuned 14B beat GPT-5-Codex on RustEvo2 and lost on hold-out ([Strand](https://huggingface.co/blog/Fortytwo-Network/strand-rust-coder-tech-report)). These wins are real but selective: tuned models improve on the task family they trained on and often regress elsewhere. On a Django study, 13 of 18 cross-task checks degraded ([Shibaev et al.](https://arxiv.org/html/2608.13566v1)). The training data has to cover every task family the owner cares about.

**(c) Matching at lower cost: real, but not through speed on this rig.** Composer 2.5 scored 62 against Opus 4.7 max at 66, at $0.07 against $4.10 per task, on a 1T base ([Artificial Analysis](https://artificialanalysis.ai/articles/cursor-composer-2-5-coding-agent-index)). On the rig, cost is time, and by estimate a dense 9B does not save time. Its real advantage is memory: 5.38 GB at Q4_0 ([Unsloth GGUF](https://huggingface.co/unsloth/Qwen3.5-9B-GGUF)) against 20.4 GB for Ornith-1.5-35B ([Ornith-1.5-35B page](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/models/ornith-1.5-35b/README.md)). By my reading, that makes a 9B relevant to small rigs of three or four cards, which the project's any-card-count rule covers, rather than to the nine-card flagship.

**The claim worth making** is narrow and testable: *on Elixir repositories it never saw, a tuned model solves more tasks per rig-hour than Flint and than its own base with a good context file, with paired statistics and a margin fixed in advance.* The likely winner of that claim is a tuned Ornith-1.5-35B. It shares tokenizer, `<think>` and `<tool_call>` conventions with Qwen3.5-9B, so data and templates carry over, and it starts at SWE Pro 59.6 and Terminal-Bench 2.1 67.8 with a Multilingual score of 71.4 ([Ornith card](https://huggingface.co/ornith-ai/Ornith-1.5-35B-A3B)). The honest risk is that LoRA barely reaches it. One author's tune of the sibling Qwen3.6-35B trained 0.024 % of the model, because the experts are fused tensors ([card](https://friendli.ai/models/srallaba/tarak-qwen3.6-35b-a3b-rsi-v1)), and SFT on an already agentic 35B added only 43.8 to 50.0 on Doc2Repo ([DeNovoSWE](https://arxiv.org/html/2606.10728)).

## The 3–5× speed edge exists only against dense 27B models

The first brief assumed a 9B runs 3–5× faster than bigger models on the rig. **That is wrong for the models that matter, and the owner should read it plainly.** Rig speed follows bytes read per token, not total parameters. A 256-expert model reads 8 of 256 experts per layer ([Ornith-1.5-35B page](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/models/ornith-1.5-35b/README.md)), so a 35B-A3B activates about 3B per token against 9B for a dense model. Bytes per token are about 4.8 GB for Qwen3.5-9B (est.), 2.1 GB for Ornith Q4_0 and 15.33 GB for Qwen3.8-27B. Every figure below that is not marked measured is an estimate scaled from project anchors.

| Model, file | tok/s on v2.0 | With planned work | Status | Against Flint's 45 |
|---|---:|---:|---|---:|
| Flint Q8_0, 262k | **44.6–45.9** (29.3 unpipelined) | — | **Measured**, agent check | 1.0× |
| Qwen3.6-35B-A3B Q4_0 | 29.0–31.1 | 39–48 (est.) | Measured on v1, one request | ~0.65× |
| Ornith-1.5-35B Q4_0 | 29–31 | 39–48 | **Estimate**, never run | ~0.65× |

| Laguna XS 2.1 Q8_0 | 22–24 (33–38 pipelined) | ~38 | Estimate, CUDA path unverified | 0.5–0.8× |
| **Qwen3.5-9B Q4_0** | **19–23** | 23–33 | **Estimate**, never run | **0.4–0.5×** |

Anchors are the project's [Flint](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/models/flint/README.md), [Qwen3.6](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/models/qwen3.6-35b-a3b/README.md) and [model branches](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/docs/research/notes/model_branches.md) pages. Against the dense 27B the 9B's edge is about 2.5–5× (est.), which is where the working assumption fits. Against Flint it is about half, and against 3B-active models about 0.6–0.8× today. The candidates note's 1.5–2× for 3B-active over 9B slightly overstates its own table, which gives 1.3–1.6× on v2.0 and up to about 2× with planned work. Dense Qwen3.5 also has no pipelining on v2.0: `--pipe-depth` fails on hybrid recurrent models until the built but untimed Q162 work lands. Ornith is hybrid too, so its 39–48 depends on the same work ([model branches](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/docs/research/notes/model_branches.md)).

Three arguments in the notes rest on the old assumption, and each has to change. The **interpolated +4 points** came from a 4× speed edge: half of SWE-Lego's +7.4, by log-interpolation. Against the dense 27B at 2.5–5× (est.) it survives as about +2 to +4, still far below the 27B's 14–17 point SWE Pro lead. Against Flint it reverses, because Flint gets about twice the attempts in the same wall clock, worth +1.6 to +1.9 on the same interpolation (my arithmetic). The **9B-first router** only pays when the first model is cheaper in time, so it fails against Flint and Ornith, where the 9B is both slower and weaker. It survives only in front of a dense model, which the project already avoids on the rig, and it should stay parked unless a measurement revives it. **"Successes per rig-hour" as the definition of winning** remains the right metric, but its expected direction flips: it now favours the 3B-active models, and the tuned model has to earn its place on pass rate. The Elixir verifier argument (compiler, `mix test`) still holds, and it helps whichever model is faster.

Tuned models also tend to take more steps and longer turns ([Tmax](https://arxiv.org/html/2606.23321)), so token speed overstates task speed. A small model that is truly fast here needs few active parameters, not few total ones. That points to Mellum2.1 12B-A2.5B, which scores SWE Pro 28 against Qwen3.5-9B's 32.0 ([BenchLM](https://benchlm.ai/models/mellum2-1-12b-a2-5b-thinking)), or LFM2.5-8B-A1B, whose makers say it is not the best fit for heavy programming ([card](https://huggingface.co/LiquidAI/LFM2.5-8B-A1B)). Neither has a rig estimate. The dense-9B speed thesis should be closed by a single timed run on the rig, not by more argument.

## Elixir has one agentic benchmark, and it belongs to the owner

The notes appear to conflict but are describing different things. The evidence supports this reading: **exactly one agentic Elixir benchmark exists, it is the owner's own, and all the others are single-turn.** `small_vs_big_evidence.md`'s "none found" is too strong, since it missed the owner's bench, and its "no Elixir-specialised model" is plainly wrong given jmarceno's public weights. `agentic_vs_sft_data.md`'s "no public Elixir SWE-style benchmark" is out of date for the same reason. `model_candidates.md`'s "no Elixir score under 39B" is true only for agentic work.

|---|---|---|---|---|
| **Elixir SWE Bench** (owner) | Agentic: repairs and features from real PRs, Docker, executable grading | 20 cases, protocol v5 | Sonnet 5.5, Opus 5.5, two Flash-Next files, two Ornith-122B files, Flint | **Primary** |
| jmarceno harness | One module per task, compile plus tests, one completion | 128, private | Gemma 12B, Qwen 3B | Comparison only; tasks unavailable, no frontier score |

| [McEval](https://ar5iv.labs.arxiv.org/html/2406.07436), [LeetCode test](https://hackernoon.com/comparing-llms-coding-abilities-across-programming-languages) | Single problem | ~50, 100 | Older models | Show Elixir is not as easy as AutoCodeBench implies |
| [MultiPL-E](https://github.com/nuprl/MultiPL-E) | Single function | HumanEval and MBPP | Very small models only | Little value |

**What the owner's bench is and where it lives.** The repository is `github.com/Cinderella-Man/elixir-swe-bench`, where the note's `elixir-agent-benchmark` is the protocol name, and the results page reads `results.json` ([results](https://cinderella-man.github.io/elixir-swe-bench/results.json)). Pi edits a broken project in a fresh Docker workspace and executable checks grade the patch, with no AI judge and no speed score. Each case comes from a real upstream PR, across Livebook, Plausible, Operately, Ash, Absinthe, Cachex, Guardian and others. The note's mismatch between eleven and twenty cases is settled: eleven was the original freeze, earlier runs were deleted on 2026-10-26, and the release was rebuilt to 20 ([ADR 0012](https://github.com/Cinderella-Man/elixir-swe-bench/blob/main/docs/adr/0012-rebuild-release-and-validate-with-unpublished-opus-runs.md)).

**How far it can be trusted.** The note read it through a summarising fetch, so I checked the owner's local checkout directly. All seven series match to the case count: Sonnet 5.5 36 of 40, Opus 5.5 53 of 60, Gyro-L 11 of 20, GSQ-RCO 10 of 20, Ornith-122B 7 and 6 of 20, Flint 6 of 20. So the transcription risk is closed, and the numbers are genuine records of those runs. They still carry four real limits. **Selection:** every case survived two reviewed Opus passes, with two kept on the owner's word despite Opus misses, and the last two validation runs count toward Opus's series. The page itself says this favours Opus slightly, and the same selection helps Sonnet. **Harness:** Claude ran through Claude Code and local models through pi, and the bench's own glossary says that comparison confounds model with harness, so 88–90 % against 30–55 % is not a clean model gap. **Seeds:** every local series has one seed of three, and on 20 cases 6/20 has a 95 % interval of about 15–52 %, and 11/20 about 34–74 % (Wilson, my calculation), so the local ranking is unresolved. **Resolution:** the agentic note's power estimate scales to about 60 paired attempts for a 20-point gap, so even a full three-seed series resolves only large differences, and less once clustering is counted. In its favour, the graders are unusually well policed: reviews kept finding wrong solutions that passed, then hardened 16, 15, 9 and 8 cases across four batches.

The bench is the right primary yardstick, but it cannot prove a 10-point gain alone. It needs a larger lane of 60–80 held-out repository tasks beside it. Its projects must also stay out of training, and the held-out list recorded in the notes (Livebook, Plausible, GenStage, the Nimble libraries) is now too short. The 20 cases add Ash, Absinthe, Cachex, Guardian, Accent, Beacon, LiveBeats, Operately, Pinchflat and Vutuv, and Ash is among the Hex packages the agentic note names when it checks licences. Task mining must exclude all of them.

## The owner's dataset is strong evaluation material, not training data

**Item quality is high and the data is narrower than its size suggests.** The audit read 28 tasks and found correct, sometimes excellent gold code and strong tests: 7,269 tests over 335 roots, median 21 per root, with a median semantic-mutant kill rate of about 86 % ([repo](https://github.com/Cinderella-Man/elixir-sft-dataset)). Unique gold text is about 2.6M tokens, against a headline of about 56M that is mostly prompt context. Coverage is the first weakness: 181 of 335 roots are GenServers, zero use LiveView, Channels, Oban or `gen_statem`, and only 6 are multi-file. Prompts are over-specified spec sheets, every LLM check is Claude, and validation has 17 roots with one real leak, where ideas 065 and 070 are the same Saga problem ([065](https://github.com/Cinderella-Man/elixir-sft-dataset/blob/328195bb/tasks/065_001_saga_compensating_transaction_coordinator_01/prompt.md), [070](https://github.com/Cinderella-Man/elixir-sft-dataset/blob/328195bb/tasks/070_001_saga_compensating_transaction_coordinator_01/prompt.md)). **No training run on it is recorded, so "good" means verified, not shown to help.** The honest comparison numbers are 335 roots, about 2,600–3,200 examples after a quality filter, and 14,803 raw rows. That filtered size is close to the 1.7K–4.7K verified rows behind jmarceno's +11 points, though those also had continued pretraining of unknown size and up to 909 preference rows ([elixir-sft](https://huggingface.co/datasets/jmarceno/elixir-sft)).

There is also a mismatch the audit did not draw out. The dataset's depth in OTP and BEAM fits the failures measured on small models, such as OTP 2/16 and binaries 0/16 at base ([Gemma card](https://huggingface.co/jmarceno/Elixir-Gemma-4-12B), [Qwen card](https://huggingface.co/jmarceno/Elixir-Qwen2.5-Coder-3B)). The owner's bench, though, is largely real application work, which by my reading of the case list sits in the half of Elixir the dataset barely covers. Even if cleared, this set would not train toward the bench it would be judged on.

**Agentic data is needed because single-turn data has no demonstrated effect inside a loop.** I found no controlled study showing that it does. Single-turn strength did not carry over: base Qwen2.5-Coder-7B fell from 52.92 to 0.0 once wrapped in a 10-step scaffold ([Shibaev et al.](https://arxiv.org/html/2608.13566v1)). Jane Street found raw code did not teach editing and moved to prompt-to-diff examples plus RL against builds ([talk](https://ai.engineer/talks/building-ai-powered-developer-tools-at-jane-street)), and jmarceno's own card excludes multi-turn use. Modern bases already run a loop, so the question is no longer "can it call tools" but "does it know Elixir and recover from `mix` errors". The project already has most of the pipeline: fresh sandboxes, gates, session files whose `gen_ranges` give the loss mask, and an Elixir pilot in which Flint verified 4 of 7 sessions ([agentic data pipeline](https://github.com/Cinderella-Man/llms-on-crypto-mining-rigs/blob/v3/bench/agentic_data/README.md)). Published data suggests a first knee at 800–1,500 sessions if R2E-Gym's 14B behaviour carries over, so about 2,000 tasks from 25–40 packages is the right first order. Cheap parser-based bugs gave 93 % of the value of mirrored PRs in the one ablation available ([SWE-smith](https://arxiv.org/html/2504.21798v2)), and real issue text should be skipped since back-translated statements matched it ([R2E-Gym](https://arxiv.org/html/2504.07164v1)).

### Provider terms block training, and private use does not escape them

Nothing here is legal advice, and the terms were read through a summarising fetch, so the clauses must be read in the original before any decision. Generation ran through `claude -p --model opus` on a subscription login, and the ledger shows 7,035 Opus calls ([repo](https://github.com/Cinderella-Man/elixir-sft-dataset/blob/328195bb/lib/gen_task/opus.ex)). Anthropic's consumer terms, effective 2025-10-08, bar using the services to develop competing products and name developing or training AI models inside that clause, so under that text alone whether an Elixir tune counts as competing is an open question ([Consumer](https://www.anthropic.com/legal/consumer-terms)). The commercial terms bar training competing models without approval ([Commercial](https://www.anthropic.com/legal/commercial-terms)). The Usage Policy, effective 2026-11-12, is broader: it binds every user and lists using outputs to train an AI model, with model distillation as an example, as needing prior authorization ([AUP](https://www.anthropic.com/legal/aup)). The owner's rule is stricter than any of these: every byte must trace to an approved source, Elixir's own generators, Flint or the owner, and the owner called unpublishable sources "useless". The repository also has no licence file at all, the April roots came from an unnamed LLM, and which plan applied is unrecorded. Those are three separate questions: others' right to use the repository, provider terms, and copyright in machine-generated text.

| Use | What enters the model | Provider terms as read | Owner's rule | Plain consequence |
|---|---|---|---|---|
| **Evaluation only** | Nothing | Weakest conflict; the clauses address training and developing models, and whether scoring counts is unsettled | Rule covers generating, training, calibrating and stores; scoring is outside it | **Go,** kept private, with scores publishable and harnesses unpublished until the licence is decided |
| **Private use** | Claude text in weights | Still conflicts: the wording does not turn on publication | Fails | **Not clean.** At most a one-off measurement the owner knowingly accepts; neither weights nor numbers can ship |
| **Published model or dataset** | Claude text in weights or files | Conflicts unless the provider authorises it | Fails | **Blocked** until written authorisation exists or Claude-written text is replaced |
| **RL on the harnesses** | Prompts and rewards derived from Claude text | Treat as training | Fails | Not a way around the problem |

Used as an evaluation set, all 335 roots on a model that never trained on them give a standard error of about ±2.7 points, against ±12 for the 17-root validation split. That is a better use than the split it was built for, and it dissolves the Saga leak. It needs a container, since candidate code executes, and looser warning and style terms for small models.

**The same terms rule out the common public trajectory sets.** SWE-Gym used gpt-4o and Claude ([paper](https://arxiv.org/html/2412.21139v2)), R2E-Gym used Sonnet ([paper](https://arxiv.org/html/2504.07164v1)), SWE-smith used Claude and o3-mini ([paper](https://arxiv.org/html/2504.21798v2)), and DataClaw exports Claude and Codex sessions ([repo](https://github.com/peteromallet/dataclaw)). OpenAI and Google carry similar clauses ([OpenAI](https://openai.com/policies/terms-of-use/), [Google](https://aistudio.google.com/docs/terms)). OmniCoder-9B's 425K+ traces come from Claude, GPT and Gemini models ([card](https://huggingface.co/Tesslate/OmniCoder-9B)), so it is a yardstick and cannot be a base under the owner's rule, whatever its Apache-2.0 tag says. Lambda's traces pass on teachers, but who wrote the prompts is unstated ([Lambda](https://huggingface.co/datasets/lambda/hermes-agent-reasoning-traces)). OpenSWE's teachers pass, but its licence statements conflict ([card](https://huggingface.co/datasets/GAIR/OpenSWE)).

**Open-weight teachers run locally avoid the problem**, and the notes differ on how far each licence was verified. Treat these three groups separately. Hosted APIs for open models bring in the host's terms, which nobody has read.

Flash-Next has the best local Elixir score, and the owner plans to try it as a teacher. DeepSeek-V4.1-Flash-1017 may be stronger still and runs on two RTX 3090s through [dsx](https://github.com/lxe/dsx) at a self-reported 32–41 tok/s, but it has no Elixir score, its 252 GB file has no agentic evaluation, and it appears to run one conversation at a time, so it suits a small gold set better than bulk sampling (est. 5–10 kept sessions per hour). Flint is the fallback that needs no new decision, and at its bench rate of 30 % (one seed) a 2,000-session set needs about 6,700 attempts, or 43–56 hours of sampling (my arithmetic, and pessimistic, since the bench's cases are harder than mined tasks). Teacher yield matters more than teacher strength, since only verified sessions are kept, but a teacher that fails most Elixir tasks teaches its own habits. That is why the trial below compares the teachers before any long run.

## Ornith-1.5-35B is the likely product, and 9B is the workbench

The candidates note ranks Qwen3.5-9B first and says no ~9B has strong agentic numbers, while `small_vs_big_evidence.md` reports Ornith-1.5-9B at SWE Pro 47.5 and MiMo's distill at 44.6. Both are right about different things: Qwen3.5-9B is the plain base, and the candidates table omits those two stronger 9Bs. By vendor numbers they start well above raw Qwen3.5-9B at 32.0, so **they enter the baseline before the pilot base is chosen**, subject to reading their licences and data provenance. Ornith-1.5-9B's base is not stated by its repo ([Ornith](https://github.com/deepreinforce-ai/Ornith-1)). Harness also moves these scores by as much as tuning: Qwen3.5-9B reads 16.1 or 27.0 on TB 2.1, and 44.0 or 60.0 on SWE Verified, depending on who ran it ([Tmax](https://arxiv.org/html/2606.23321), [MiMo](https://huggingface.co/XiaomiMiMo/MiMo-V2.6-Distill-Qwen-9B)). The 9B stays useful as a workbench. Each copy fits one card, so five parallel experiments run at once, every weight is reachable and merging is simple. It also has a `-Base` checkpoint for the knowledge stage, which the language literature ranks as the strongest recipe: continued pretraining from base, then restoring instructions ([Gleam](https://arxiv.org/html/2606.16827v1)). Curated data beats volume by a wide margin here: 25K clean Kotlin files gave +11.8, while 4M raw files gave +1.2 to +3.1 ([Kotlin](https://arxiv.org/html/2405.19250v1)). The comparison of `gemma12b-elixir-cpt-q4` at 40 with the base at 31 and the release at 46 hints that this stage did most of jmarceno's work, though that is a lead rather than a finding, because the checkpoint's recipe is unstated ([preference data](https://huggingface.co/datasets/jmarceno/elixir-preference)). The agentic note ranks this stage low, but for a model whose gap is Elixir knowledge the language evidence ranks it first. It runs on licence-scanned Hex code, so it is the clean replacement for the blocked SFT set.

The export path is settled: merge in PyTorch onto the BF16 base, convert, run imatrix, quantize and relay, in under an hour (est.). Do not serve a live `--lora` on the rig: Pascal kernel matching is built around the plain graph, so it would likely lose kernel speed (an untested inference). A merged file needs its imatrix and any screen or drafter files rebuilt, and MTP acceptance can fall. When a tune behaves worse after export, check the chat template and EOS token first ([Unsloth](https://unsloth.ai/docs/models/qwen3.5/fine-tune.md)).

**All wall times here are estimates at roughly ±40 %, and none was measured on this machine.** Each comes from the training-time note's arithmetic on one third-party 3090 report for a 1.7B model ([Zagitta](https://github.com/Zagitta/gpu-unlock/issues/75)) and the 6-FLOPs-per-parameter-per-token rule, and no one has published this figure for a 9B on a 3090.

| LoRA, 20k, 3 epochs | 5 | 22 h (13 h) | 35 | 10 |

The assumptions carry the table. BF16 LoRA with gradient checkpointing at the 250 W cap runs at **180 tok/s per card likely, 280 best**. DDP efficiency of 0.85 (0.92) gives **765 (1,290) tok/s** on five cards. At 20k-token lengths the per-card rate falls to 145 (240), and a quantized base multiplies by 0.8. PCIe is assumed at x8, x8, x4, x1, x1, as last recorded. Power is 1.6 kW at the wall and price €0.30/kWh, both to be scaled to the real tariff. Teacher generation rests on one measured local rate of 62 sessions per hour on two 3090s, and keeping only passes doubles those times. No row times an Ornith run, so by the candidates note's rough ratio expect about 1.7× the 9B's time on four cards, with memory at agent length unknown.

Memory, not compute, is the real limit. Unsloth states no sequence length for its 22 GB figure, and the note's memory model reproduces it at about 2k tokens (est.). Ceilings for one 3090 at batch 1 are about **6–8k tokens in BF16, 16–18k in 8-bit and 24–29k in 4-bit** (est.), so 32k sessions do not fit one card. This settles a conflict between the notes: `agentic_vs_sft_data.md` defaults to QLoRA and a 32k cap, but Unsloth advises against 4-bit on every Qwen3.5 model ([Unsloth](https://unsloth.ai/docs/models/qwen3.5/fine-tune.md)). Test 8-bit first and keep sessions under about 16k by cutting old tool output at turn boundaries. Full-weight training needs 72–88 GB, so it works only by sharding, and five cards then give about 2.5–3.9× one card. LoRA barely notices the x1 links: its 160 MB gradients sync in about 0.3 s, roughly 1 % of a step (est.; no source measures DDP on x1). One LoRA per GPU is the best mode for sweeps, because it needs no sync at all.

Keep the 250 W cap, which costs 7–17 % of speed and saves 8–18 % of energy (est., from [Puget](https://www.pugetsystems.com/labs/hpc/quad-rtx3090-gpu-wattage-limited-maxq-tensorflow-performance-1974/) and Zagitta). Five cards use less energy per token than one, since idle cards draw power anyway. [RunPod](https://www.runpod.io/pricing) lists five 3090s for the 20k LoRA at $24–$55 against about €10 at home, so home wins on cash by 2–5×. Rent when a job needs 8k+ tokens in BF16 per card, because 80 GB cards remove the memory problem outright. The true price of a home run is the queue: the owner has put the Flash-Next rows first on both machines, and those rows wait while training holds the cards.

The stack is Unsloth with `torchrun` for LoRA, a separate vLLM 0.33 container for generation, and Axolotl 0.21 as the fallback for sharding, all via containers so the host's driver stays untouched (versions from [PyPI](https://pypi.org/pypi/unsloth/json)). rLLM and verl come in only if multi-turn RL gets a go. Whether vLLM 0.33 supports Qwen3.5 well enough for GRPO is unconfirmed.

## Eight stages, each with a cheap kill line

Several gates apply before anything runs, and all of them are the owner's call or need a fresh check. **The smoke test needs the owner's explicit OK**, because the quant machine's rules forbid speed measurements there while allowing training runs, and timing a run on purpose is a speed test. Pass-rate evaluation stays compliant with the bench's timing observer disabled, and speed results come from the rig in a quiet window. **Every download needs the owner's OK**, including all the 9B candidates, after an inventory check. **PCIe widths must be rechecked under load**: x8, x8, x4, x1, x1 is an older record, the two newest 3090s sit in the V100s' old slots, and links drop at idle. **The Ornith BF16 and imatrix must be located first**, because any converted file may need rebuilding. Decisions the owner must record: the dataset's provenance verdict, the extended held-out list, and which teachers go on the writer list.

| Stage | Work | Cost (est.) | Kill line |
|---|---|---:|---|
| **1. Evaluation lane** | Elixir SWE Bench under pi, timing off, three seeds: Qwen3.5-9B, Ornith-1.5-9B, MiMo distill, Ornith-1.5-35B, Flint's missing seeds. Owner's 335 roots as a single-turn lane. Build 60–80 held-out repo tasks and ~40 Exercism tasks in `bench/agent_check` | Days of bench work, 2–3 GPU days | Stop the 9B as a product if the best 9B is 20+ points below Ornith-35B or solves ≤ 2 of 20 |
| **2. Context arm** | Docs index and usage rules, from permissive docs or written by the owner or Flint, on the best base, same lanes | Days, ≤ 1 GPU day | If context alone adds ≥ 15 points, ship it and stop; that exceeds the best Elixir tune ever reported |
| **3. Rig speed check** | One timed agent check of Qwen3.5-9B Q4_0, and Ornith Q4_0 once available | 5.4 GB download, ~1 rig day | If minutes per solved task do not beat Ornith's, the 9B is a workbench only and the router stays parked |
| **4. Smoke test** | Links, `nccl-tests`, 200-step LoRA, sequence sweep, DDP, vLLM, merge to rig | 1 day, owner's OK | Stop long runs if a card is below ~100 tok/s or DDP below 3×; stop all if a merged file loses tool calling on the rig |
| **5. Task factory and teacher trial** | AST bug transforms, commit mining on 25–40 approved packages, 200 pilot tasks; the candidate teachers on 50 tasks, 4 attempts each | CPU, 1 GPU day | Stop if the best approved teacher verifies < 20 % (over 3 days of sampling for 2,000 kept), or tasks fail the gates at scale |
| **6. 9B pilot** | 500 kept sessions; five one-card arms including a curated Hex knowledge stage; then 1,000 and 2,000 | ~1 day per round at 500, plus ~8 h sampling | At 500: stop if tuned falls below base or malformed tool calls rise. At 2,000: stop if the paired gain over base-plus-context includes zero on ≥ 230 attempts |
| **7. Port to Ornith-35B** | Same data, LoRA on shared expert, attention and Gated DeltaNet, four cards | ~1.7× the 9B's time | Stop if gain is under half the 9B's, or the merged file loses tool discipline; ship base plus context instead |
| **8. RL, gated** | Single-turn GRPO on clean tasks, 300 iterations; then 60-step multi-turn, from-base and from-SFT arms | 28 h; 2–5 d per arm | Close RL unless the repo lane gains ≥ 3 points or time per success clearly drops |

The kill thresholds are judgement calls, not published standards, and they should be fixed before each run, as should the decision rule for "beats". Scoring should stay three-armed (base, tuned, opponent), because without the base arm any win could be size or speed rather than training. Primary score is hidden `mix test` passing with tests unchanged. Compile warnings, format, Credo and Dialyzer are reported separately and never used as rewards, since a static-analysis reward alone made a small model worse ([Skopin and Kotelnikov](https://arxiv.org/html/2605.30478v1)). Held-out commits should postdate the models' training cut-offs, which repository holdout alone cannot guarantee. Stage 1's model list is the one piece that can be started as soon as the machine is back, and it is also where the most assumptions in this report get replaced by measurements.

## Conclusion

The question changed under investigation. It began as whether a small model can beat a big one, but on Pascal cards "small" means few active parameters, not few total parameters, so a dense 9B is a mid-sized model on this rig and Ornith-1.5-35B is the small one. The contest that matters is therefore not 9B against 35B but tuned against untuned within the 3B-active class, with Flint as the untunable champion to pass. A dense 9B keeps two real jobs: it is the fastest workbench for proving a recipe, and it is the model that fits a three-card rig, which is a mission argument rather than a benchmark one.

The most durable output may not be a model at all. A clean, publishable Elixir agent dataset and the first measured language-specific agentic result, on a bench with unusually hard-won graders, would outlast any single tune, since new base generations arrive within months and could erase a LoRA's gain. The dataset that started the question is valuable in the opposite way from how it was built: its tests are worth more than its answers.
